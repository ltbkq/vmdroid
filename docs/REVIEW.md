# 设计文档多 AI 评审规程（Review Protocol）

**目标**：今天内用**多个 AI × 多轮**把 `DESIGN.md` / `IMAGE-FORMAT.md` / `README*.md`
优化到可开工状态，每轮结论落盘、可追溯、可回归。

---

## 1. 角色分工（每轮并行 N 个评审者）

每个评审者只负责一个视角，**不重复**、**不越界**，输出必须落到 §3 的格式。

| 角色 | 审什么 | 不审什么 |
|---|---|---|
| **A · 一致性** | 三份文档互相矛盾、章节引用失效（§x.y 指错）、表格数值不一致、术语漂移 | 技术方案对不对 |
| **B · 技术正确性** | 底层事实是否成立（squashfs 尾随数据、QEMU/AVF 能力、Android 存储/SAF、dropbear/systemd 配置、端口链路） | 需求覆盖 |
| **C · 需求覆盖** | 用户原始需求是否每条都有落点 + 有验收标准（见 §5 需求基线） | 文风、排版 |
| **D · 可实施性** | 拿到文档能否直接开工：缺哪些字段、哪些步骤、哪些工具、哪些测试；工作量/里程碑是否合理 | 重新做产品决策 |

---

## 2. 轮次与通过条件

| 轮 | 范围 | 退出条件（全部满足才进下一轮） |
|---|---|---|
| **R1** | 全文，4 角色并行 | 所有 `Blocker`/`Major` 已定性（接受/拒绝/改期），无未归类问题 |
| **R2** | 针对 R1 修改处 + 4 角色复审 | `Blocker = 0` 且 `Major = 0` |
| **R3** | 冻结评审：仅一致性 + 需求覆盖 | `Blocker/Major = 0`，`Minor` 已登记不阻塞 |

**严重度定义**

| 级 | 定义 | 处理 |
|---|---|---|
| `Blocker` | 会导致实现失败 / 需求不满足 / 文档自相矛盾到无法执行 | 当轮必修 |
| `Major` | 会造成返工、返工成本高、或关键路径遗漏 | 当轮必修 |
| `Minor` | 表述/排版/次要遗漏 | 登记，R3 前清 |
| `Info` | 建议、备选方案、未来工作 | 记录，不强制 |

---

## 3. 问题单格式（每个评审者统一输出）

```markdown
### <角色字母>-<轮>-<序号> · <严重度>
- **位置**：`docs/DESIGN.md §4.5`（或行号）
- **问题**：一句话说清"哪里错了/缺了"
- **依据**：为什么错（事实/需求条目/交叉引用）
- **建议**：具体改法（给出替换文本，不要只说"需要补充"）
- **成本**：<改动范围：一行 / 一节 / 需重新决策>
```

汇总落盘到 `docs/reviews/R<n>.md`，头部带统计表。

---

## 4. 评审输入（给外部 AI 的话术）

把下面这段 + 待评审文档全文一起发给另一个 AI 系统：

```text
你是资深系统架构评审员。请评审以下设计文档，严格按"问题单格式"输出，
按严重度 Blocker/Major/Minor/Info 分组。不要复述文档内容，只输出问题。
要求：(1) 每条必须给出精确位置（章节号/行号）与可执行的替换文本；
(2) 对技术断言要做事实核查，存疑就标注"待验证"并说明如何验证；
(3) 若文档之间（DESIGN / IMAGE-FORMAT / README）互相矛盾，必须点名两处；
(4) 不要提出与已有决策冲突的新产品方向，只指出决策未落地之处。

<此处粘贴 docs/DESIGN.md>
<此处粘贴 docs/IMAGE-FORMAT.md>
<此处粘贴 README.md>
```

> 建议至少换 **3 个不同厂商**的模型各跑一次（角色 A/B/C/D 任选分配），
> 再把三份结果合并进 `R1.md`，去重后按严重度排序。

## 5. 需求基线（角色 C 的核对清单，源自用户原话）

| # | 原始需求 | 落点 | 验收标准 |
|---|---|---|---|
| R-01 | 软件与系统分开 | DESIGN §1.2 G1、§2 | APK 不含 rootfs |
| R-02 | 系统是单独的 `.img` 文件 | DESIGN §1.2 G2、IMAGE-FORMAT 全文 | 单文件可独立分发/校验 |
| R-03 | 系统**可以更换** | DESIGN §4.7、§5.1–5.3 | 换镜像不重装应用、不改代码 |
| R-04 | 虚拟机功能**参照 Podroid** | DESIGN §3 对照表 | 逐子系统 1:1，契约零改动 |
| R-05 | 首发只做一个 `debian.img` | DESIGN §4.5 | 单一首发镜像 |
| R-06 | **最小化安装** | DESIGN §4.5 包集合 | 不装桌面环境/容器栈 |
| R-07 | 后续系统慢慢增加 | DESIGN §4.7 路线图 | 新镜像不需应用发版 |
| R-08 | 新系统要装 **SSH** | DESIGN §4.5/§4.8 | dropbear 在 `Ready!` 前可用 |
| R-09 | 增加用户名 **`ltbkq`** | DESIGN §4.8 | `useradd ltbkq` 存在于镜像 |
| R-10 | root 与 ltbkq **默认密码均 `123`** | DESIGN §4.8 | 两账户 shadow 哈希存在 |
| R-11 | 两账户**均可 SSH 登录** | DESIGN §4.8、§13.2 | 两条 `ssh -p 9922` 均成功 |
| R-12 | SSH **默认端口 22** | DESIGN §4.8 端口表 | guest 内监听 22，不改端口 |
| R-13 | img 镜像**可安装 Xvnc** | DESIGN §4.5/§4.6、§13.2 | `:5900` 可连，X11 入口可用 |
| R-14 | 应用内下载 + 手动导入 | DESIGN §6 | 两条路径都可安装镜像 |
| R-15 | （评审补充）首次运行无镜像须引导且不启动死机 | DESIGN §7.4/§8.4 | 引导页出现且 VM 不进挂载失败态 |
| R-16 | **`.img` 在 Linux PC 端可用 QEMU 正常启动** | DESIGN §11.4 + IMAGE-FORMAT §2/§3 | x86_64 Linux + `qemu-system-aarch64` 一条命令启动 → 进入 `Ready!`/登录提示 |

> 评审时若发现某条需求**只有落点没有验收标准**，或**验收标准与落点不一致**，按 `Major` 报。

---

## 6. 落盘约定

```
docs/
  DESIGN.md · IMAGE-FORMAT.md · README.md · README.en.md   ← 被评审对象
  REVIEW.md                                                  ← 本规程
  reviews/
    R1.md   R2.md   R3.md        ← 每轮问题单 + 处理结论
    FEEDBACK-EXT.md              ← 外部 AI 原始返回（粘贴区）
```

- 每轮评审**只读** `docs/*.md`（评审期间禁止修改被评审文档，避免评审对象漂移）。
- 问题定性后统一修改，**修改即 commit**，commit message 写 `review(R<n>): <n> fixes`。
- 一轮结束更新 §2 的统计表，作为下一轮输入。
